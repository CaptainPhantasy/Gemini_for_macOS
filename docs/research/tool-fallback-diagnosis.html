Tool-Call Fallback Diagnosis

Why the model returns "Tool execution completed, but the model did not provide a final summary" instead of a natural language response

🔍 Problem Statement

When the agent executes one or more tool calls (e.g. google:search, google:ds_python_interpreter), the model successfully runs all tools across multiple iterations but then falls through to the synthetic fallback message instead of producing a natural-language summary of what it found.

Root Cause

The responseText variable only accumulates text via the onChunk streaming callback. When the model response contains only functionCall parts across all 10 iterations — no text parts — responseText remains empty, and the fallback at line 793 fires.

🔌 Root Cause Analysis

1. responseText only accumulates text chunks

At App.tsx:668-671, the onChunk callback sets responseText = chunk.aggregatedText. When the streaming response delivers only functionCall parts — which is the normal pattern for tool-using models — aggregatedText stays "".

// App.tsx:668-671 — onChunk callback
onChunk: (chunk) => {
  responseText = chunk.aggregatedText;  // empty when only functionCall parts
  upsertStreamingModelMessage(chunk.aggregatedText); // shows empty bubble
},

2. No text parts in model response

At App.tsx:675, extractResponseParts(response) returns { functionCalls: [...], text: "" } when the model emits only functionCall parts. Since functionCalls.length > 0, the loop continues (line 719-752) — but responseText from line 674 is "".

// App.tsx:674-676
responseText = result.responseText || responseText;
const { text, functionCalls } = extractResponseParts(response);
// text = "" when only functionCall parts exist

3. No mechanism to force a summary generation

The loop (lines 651-787) has three exit paths:
• Line 704-715: Budget exceeded — breaks with cost/thinking message
• Line 719-752: functionCalls.length > 0 — execute tools, continue to next iteration
• Line 786: No function calls — break with whatever responseText contains

When path 2 runs for all 10 iterations, path 3 never executes, and responseText is still "". The fallback then fires at line 793.

4. Context window truncation (40-message limit)

At App.tsx:610-612, the conversation window is trimmed to MODEL_CONTEXT_MESSAGE_LIMIT = 40 messages. Each tool round adds 2+ messages (model + user/tool-response). After 10 iterations, the model may lose visibility into earlier instructions including the "respond in natural language" system prompt.

// App.tsx:610-612
const workingMessages = updatedMessages.length <= MODEL_CONTEXT_MESSAGE_LIMIT
  ? updatedMessages
  : updatedMessages.slice(-MODEL_CONTEXT_MESSAGE_LIMIT); // 40 messages max

5. The fallback message is purely synthetic

At App.tsx:793-817, the code scans workingContents for functionResponse parts and builds a text-only fallback. The model never participates in this step — it's a mechanical enumeration of tool results with no semantic understanding.

🧰 Four Fix Strategies

Fix A: Post-loop summary generation (recommended)

After the 10-iteration loop, if responseText is empty and tools were called, inject a final generation call with system instruction: "Summarize the tool results above in natural language." This gives the model one more chance with the complete tool output as context.

// App.tsx:~793 — after loop
if (!responseText.trim() && observedToolCalls.length > 0) {
  const summaryResponse = await ai.models.generateContent({
    model: selectedModel,
    contents: [
      ...workingContents,
      { role: "user", parts: [{ text: "Summarize what you found." }] }
    ],
  });
  responseText = summaryResponse.text;
}

Fix B: Real-time tool execution UX

Show users the tool execution progress during the loop so they don't see a blank bubble. The onChunk callback at line 668-671 could also stream tool-call status via upsertStreamingModelMessage.

// During loop iteration — at line 741-751
upsertStreamingModelMessage(`Running tool: ${fc.name}...`);

Fix C: Truncate large tool results

If a tool returns a very large result (e.g. 100KB+), it may push the conversation past the model's context window. Cap tool results at ~4KB before appending to workingContents.

// Before appending at line 744
const truncated = truncateToolResult(toolResult, 4_000);
workingContents.push(buildFunctionResponse(fc.name, truncated, fc.id));

Fix D: Human-readable fallback with tool output

Enhance the fallback at line 809 to include actual tool output summaries rather than the generic message. Include key findings from each tool execution.

// App.tsx:808-812 improved
responseText = `I ran \${observedToolCalls.length} tools and found:\n\n\${summarizeToolOutputs(workingContents)}`;

Most Likely Scenario

The model is executing 1-3 tool calls per iteration and stopping because it has completed its assigned task (e.g., "search for X"). Each iteration adds 2+ messages (model thought + tool result). After 4-5 iterations, the 40-message window may have trimmed earlier context. The model interprets the trimmed context as "task complete, respond" but emits only a function call — not realizing it already returned tools in prior iterations. By iteration 10, the context is dominated by tool results with no visible instruction to produce a final text answer.

Recommended fix: Fix A (post-loop summary generation pass) as primary, Fix B (real-time tool UX) as secondary for immediate user-facing improvement.
